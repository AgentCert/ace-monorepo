# 2.3 — Fault Taxonomy

## What This Section Covers

This is the reference catalog of fault types used across AgentCert experiments. Every fault in this taxonomy has a defined category, a set of observable symptoms, and a corresponding LitmusChaos experiment definition in the [chaos-charts repository](https://github.com/AgentCert/chaos-charts).

Fault prioritisation is driven by customer feedback, incident history, and business criticality. The priority column is left configurable — what matters most to your deployment is not the same as what matters to another team's.

All experiments and certification runs must reference this taxonomy. When you write a fault configuration file, the `fault_category` and `fault_name` fields must match entries here.

---

## How Faults Are Classified

Each fault belongs to one of five categories based on what layer of the stack it targets:

| Category | What It Targets | Typical Observable Impact |
|---|---|---|
| Network | Pod-to-pod and pod-to-service communication | Latency spikes, connection timeouts, DNS failures |
| Compute / Resource | CPU, memory, and disk within a pod or node | Performance degradation, OOM kills, throttling |
| Application | Pod lifecycle and container process | Service unavailability, restart loops, scaling anomalies |
| Database / Storage | Stateful workloads and I/O | Data access failures, write bottlenecks, corruption signals |
| Security / Adversarial | Access control and certificate validity | Authentication failures, unexpected traffic, connection drops |

---

## 1. Network Faults

These faults target the communication layer. They are particularly interesting for certification because the symptoms are indirect — the agent has to reason from upstream timeouts and connection errors back to a network-layer root cause.

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| Pod Network Loss | Drops network packets between pods — percentage configurable | [`pod-network-loss`](https://github.com/AgentCert/chaos-charts) ✓ *certified* |
| Pod Network Rate Limit | Throttles network bandwidth to simulate congested links | [`pod-network-bandwidth`](https://github.com/AgentCert/chaos-charts) |
| Pod DNS Error | Simulates DNS resolution failures — service discovery breaks down | [`pod-dns-error`](https://github.com/AgentCert/chaos-charts) |
| Modified Target Port Kubernetes Service *(ITBench)* | Replaces a Service's targetPort with a broken value, routing traffic to a closed port | [`modified-target-port-kubernetes-service`](https://github.com/AgentCert/chaos-charts) |
| Invalid Kubernetes Service Selector *(ITBench)* | Replaces a Service's selector with an invalid label so it matches no pods, dropping Endpoints to zero | [`invalid-kubernetes-service-selector`](https://github.com/AgentCert/chaos-charts) |
| Ingress Port Blocking Network Policy *(ITBench)* | Creates a deny-all-ingress NetworkPolicy against a workload's pods | [`ingress-port-blocking-network-policy`](https://github.com/AgentCert/chaos-charts) |
| Failing Name Resolution Kubernetes Workload DNS Policy *(ITBench)* | Points a pod's dnsConfig/dnsPolicy at an unreachable DNS server | [`failing-name-resolution-kubernetes-workload-dns-policy`](https://github.com/AgentCert/chaos-charts) |
| Deleted Kubernetes Service *(ITBench)* | Deletes the Service fronting a workload, then recreates it from a captured manifest | [`deleted-kubernetes-service`](https://github.com/AgentCert/chaos-charts) |
| Chaos Mesh HTTP Body Tamper Replacement *(ITBench)* | Approximates Chaos Mesh's HTTPChaos POST-body-tampering via synthetic malformed traffic | [`chaos-mesh-http-body-tamper-replacement`](https://github.com/AgentCert/chaos-charts) — built without Chaos Mesh; a documented partial approximation, not a faithful reproduction (see fault.yaml). |
| Chaos Mesh HTTP Abort Replacement *(ITBench)* | Approximates Chaos Mesh's HTTPChaos abort action via a port-scoped NetworkPolicy | [`chaos-mesh-http-abort-replacement`](https://github.com/AgentCert/chaos-charts) — built without Chaos Mesh; coarser than the original (blocks all traffic on the port, not just POST — see fault.yaml). |

**What the agent needs to do well:** Distinguish network faults from application faults. HTTP 5xx errors look similar whether the downstream pod is deleted or the network is dropping packets. The agent should reach for network diagnostic tools (not just pod status) when investigating.

## 2. Compute / Resource Faults

These faults target resource consumption. They produce gradual degradation rather than sudden failure — which tests whether the agent can detect and act on trend signals, not just binary outage events.

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| Pod CPU Hog | Consumes excessive CPU within a pod, causing throttling and latency | [`pod-cpu-hog`](https://github.com/AgentCert/chaos-charts) ✓ *certified* |
| Disk Fill | Fills the available disk to simulate storage exhaustion | [`disk-fill`](https://github.com/AgentCert/chaos-charts) |
| Pod Memory Hog | Consumes excessive memory — may trigger OOM kill if limit exceeded | [`pod-memory-hog`](https://github.com/AgentCert/chaos-charts) ✓ *certified* |
| Valkey Workload Out Of Memory *(ITBench)* | Clamps the valkey-cart container's memory limit/request to force OOMKilled | [`valkey-workload-out-of-memory`](https://github.com/AgentCert/chaos-charts) — Resource vs. Database/Storage were both defensible for this fault; Resource was chosen by random selection, not a strong architectural argument. |
| Insufficient Kubernetes Resource Quota *(ITBench)* | Creates/patches a namespace ResourceQuota with hard limits too low for the workload | [`insufficient-kubernetes-resource-quota`](https://github.com/AgentCert/chaos-charts) |
| Unassigned Kubernetes Workload Container Resource Limits *(ITBench)* | Removes a container's resources.limits, leaving no consumption ceiling | [`unassigned-kubernetes-workload-container-resource-limits`](https://github.com/AgentCert/chaos-charts) |
| Insufficient Kubernetes Workload Container Resources *(ITBench)* | Patches a container's requests/limits to unrealistically low values, causing OOMKilled/CrashLoopBackOff | [`insufficient-kubernetes-workload-container-resources`](https://github.com/AgentCert/chaos-charts) |

**What the agent needs to do well:** Identify the specific pod and resource under stress, not just flag that "something is slow." Recommend a targeted remediation rather than a blanket restart.

## 3. Application Faults

These are the most directly observable faults — pods disappear, containers die, replicas scale unexpectedly. They are the easiest for agents to detect and the baseline for any certification run.

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| Pod Delete | Forcefully deletes a running pod, triggering Kubernetes self-healing | `pod-delete` |
| Container Kill | Kills the main container process within a running pod | `container-kill` |
| Pod Autoscaler | Triggers unexpected horizontal scaling behaviour | `pod-autoscaler` |
| Scaled To Zero Kubernetes Workload *(ITBench)* | Scales a Deployment/StatefulSet to zero replicas, then restores it | [`scaled-to-zero-kubernetes-workload`](https://github.com/AgentCert/chaos-charts) |
| Nonexistent Kubernetes Workload Container Image *(ITBench)* | Sets a container image to a nonexistent tag, causing ImagePullBackOff | [`nonexistent-kubernetes-workload-container-image`](https://github.com/AgentCert/chaos-charts) |
| Misconfigured Kubernetes Workload Container Readiness Probe *(ITBench)* | Patches a container's readinessProbe to an unreachable port, causing the pod to stay NotReady | [`misconfigured-kubernetes-workload-container-readiness-probe`](https://github.com/AgentCert/chaos-charts) |
| Misconfigured Kubernetes Horizontal Pod Autoscaler *(ITBench)* | Misconfigures HPA utilization thresholds so it maxes out without relieving load | [`misconfigured-kubernetes-horizontal-pod-autoscaler`](https://github.com/AgentCert/chaos-charts) — Application vs. Resource were both defensible; Application was chosen by random selection. **Note:** ITBench also reuses this exact mechanism, unchanged, as its one FinOps scenario (`category: "finops"`, scenario index 38) — the same `fault_name` is framed as an availability fault here and as a cost-optimization fault there. `fault_categories.json` cannot express both framings for one fault name simultaneously; see that file's `finops_fault` entry for the resulting collision. |
| OpenTelemetry Demo Feature Flag *(ITBench)* | Toggles a named OTel Demo feature flag via the flagd-config ConfigMap | [`opentelemetry-demo-feature-flag`](https://github.com/AgentCert/chaos-charts) |
| Unsupported Architecture Kubernetes Workload Container Image *(ITBench)* | Sets a container image to an unsupported-CPU-architecture tag, causing ImagePullBackOff | [`unsupported-architecture-kubernetes-workload-container-image`](https://github.com/AgentCert/chaos-charts) |
| Crashing Kubernetes Workload Init Container *(ITBench)* | Injects an initContainer that crashes, blocking the main container from starting | [`crashing-kubernetes-workload-init-container`](https://github.com/AgentCert/chaos-charts) |
| Hanging Kubernetes Workload Init Container *(ITBench)* | Injects an initContainer that hangs indefinitely, blocking the main container from ever starting | [`hanging-kubernetes-workload-init-container`](https://github.com/AgentCert/chaos-charts) |
| Modified Kubernetes Workload Container Environment Variable *(ITBench)* | Overwrites one container env var with a bad value | [`modified-kubernetes-workload-container-environment-variable`](https://github.com/AgentCert/chaos-charts) |
| Invalid Kubernetes Workload Container Command *(ITBench)* | Overwrites a container's command with a nonexistent executable, causing CrashLoopBackOff | [`invalid-kubernetes-workload-container-command`](https://github.com/AgentCert/chaos-charts) |
| Chaos Mesh Pod Failure Replacement *(ITBench)* | LitmusChaos-native replacement for Chaos Mesh's PodChaos pod-failure action — freezes a container via SIGSTOP/SIGCONT through an ephemeral debug container | [`chaos-mesh-pod-failure-replacement`](https://github.com/AgentCert/chaos-charts) — built without Chaos Mesh; see fault.yaml for why the naive `kubectl exec ... kill -STOP` approach doesn't work against a distroless target and what was used instead. |

**What the agent needs to do well:** Detect quickly (pod delete has the shortest expected TTD of any fault category), confirm that self-healing is underway, and verify service restoration — not just that the pod is back, but that the service endpoint is healthy.

**Reference experiment:** Pod Delete was the primary fault used in the Flash Agent certification. The reference traces are in [AgentCert-Traces](https://github.com/AgentCert/AgentCert-Traces).

## 4. Database / Storage Faults

These faults affect stateful workloads and are harder to detect because the symptoms (slow queries, write failures) often surface well after the fault is active. They require the agent to investigate deeper into the stack.

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| MCP Configuration Failure | MCP server configured incorrectly — agent loses tool access | Custom |
| Pod IO Stress | Injects I/O stress affecting stateful workloads at pod level | `pod-io-stress` |
| Node IO Stress | Injects I/O stress at node level — affects all pods on the node | `node-io-stress` |
| Nonexistent Kubernetes Workload Persistent Volume Claim *(ITBench)* | Creates a PVC with an invalid StorageClass and mounts it into a workload, causing Pending/Init with FailedMount | [`nonexistent-kubernetes-workload-persistent-volume-claim`](https://github.com/AgentCert/chaos-charts) |

**What the agent needs to do well:** Not confuse I/O stress with a network fault (both produce latency). Understand that an MCP configuration failure degrades its own diagnostic capabilities — it may need to flag that its tools are not responding correctly rather than misdiagnosing a cluster fault.

---

## 5. Security / Adversarial Faults

These faults simulate misconfiguration and credential issues. They are relevant for RAI testing as well as operational certification — an agent responding to a network policy misconfiguration may inadvertently expose sensitive cluster information if it isn't careful.

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| NetworkPolicy Misconfig | Simulates misconfigured network policies allowing unintended traffic | Custom |
| TLS Expiry | Simulates expired TLS certificates causing connection failures | Custom |
| RBAC Revoke | Revokes RBAC permissions to simulate privilege escalation or access denial | Custom |
| Valkey Workload Changed Password *(ITBench)* | Changes the password of a Valkey workload, denying access to callers using the old credential | [`valkey-workload-changed-password`](https://github.com/AgentCert/chaos-charts) — Database/Storage vs. Security/Adversarial were both defensible; Security/Adversarial was chosen by random selection. |

**What the agent needs to do well:** Not over-escalate. A TLS expiry is a certificate rotation task, not a cluster-wide incident. The agent should recommend the least-privilege fix and not recommend granting broader permissions to work around the problem.

## 6. CISO / Compliance Tasks *(does not fit categories 1–5)*

ITBench's CISO domain (`itbench-hub/ITBench`, `scenarios/ciso/`) is not fault-injection-and-diagnose in the sense categories 1–5 assume — there is no LitmusChaos experiment, no golden-signal alert, and no time-to-detect/time-to-mitigate. The task is compliance-as-code policy authoring or remediation against a CIS Benchmark control. "Security / Adversarial" is the closest existing category by name, but its definition above (access control, certificate validity, authentication failures) does not describe this task type, so these are tracked as their own group rather than forced into category 5.

| Scenario Type | What It Does |
|---|---|
| `Gen-CIS-b-K8s-Kyverno` | Generate and deploy a Kyverno admission-control policy satisfying a CIS Kubernetes Benchmark control |
| `Gen-CIS-b-K8s-Kubectl-OPA` | Collect Kubernetes resource state via `kubectl`, then write an OPA Rego policy checking a CIS Kubernetes Benchmark control |
| `Gen-CIS-b-RHEL9-Ansible-OPA` | Collect RHEL9 host configuration via Ansible, then write an OPA Rego policy checking a CIS RHEL9 Benchmark control |
| `Upd-CIS-b-K8s-Kyverno` | Remediate/update an existing Kyverno policy to satisfy a CIS Kubernetes Benchmark control |

Not implemented in chaos-charts (no ChaosEngine/ChaosExperiment applies to this task type). Tracked in `certifier/configs/fault_categories.json` under `ciso_fault` so that any future CISO certification run has a category to aggregate into.

## 7. Scheduling / Node-Placement Faults *(does not fit categories 1–5)*

These faults disrupt where and whether the Kubernetes scheduler can place a pod at all — they target the scheduler/node layer, not a pod's network, resource consumption, container lifecycle, storage, or credentials. None of categories 1–5 describe "the pod can never be scheduled in the first place" as a symptom, so these are tracked as their own group rather than forced into an ill-fitting category. Symptom pattern: pod stuck `Pending` indefinitely, `FailedScheduling` events, no container ever starts (as distinct from category 3's "container starts and then fails").

| Fault | Description | LitmusChaos Experiment |
|---|---|---|
| Nonexistent Kubernetes Workload Node *(ITBench)* | Adds a nodeSelector referencing a node name that doesn't exist, leaving the pod permanently Pending | [`nonexistent-kubernetes-workload-node`](https://github.com/AgentCert/chaos-charts) |
| Cordoned Kubernetes Worker Node *(ITBench)* | Cordons the node hosting a target workload, blocking new scheduling there | [`cordoned-kubernetes-worker-node`](https://github.com/AgentCert/chaos-charts) — caution: affects all pods on the cordoned node, not just the target. |
| Priority Kubernetes Workload Priority Preemption *(ITBench)* | Creates a higher-priority PriorityClass + decoy workload to force scheduler preemption of the target's pod | [`priority-kubernetes-workload-priority-preemption`](https://github.com/AgentCert/chaos-charts) |
| Unschedulable Kubernetes Workload Pod Anti Affinity Rule *(ITBench)* | Patches in an unsatisfiable required inter-pod anti-affinity rule | [`unschedulable-kubernetes-workload-pod-anti-affinity-rule`](https://github.com/AgentCert/chaos-charts) |
| Kubernetes API Server Request Surge *(ITBench)* | Deploys a load-generator workload that surges requests against the kube-apiserver | [`kubernetes-api-server-request-surge`](https://github.com/AgentCert/chaos-charts) — caution: affects apiserver-wide latency/responsiveness for every tenant on the cluster, not just the target namespace; this is control-plane-adjacent rather than purely scheduling, grouped here for lack of a better fit among 1–5. |

**What the agent needs to do well:** Recognize `Pending`/`FailedScheduling` as fundamentally different from a crash loop — the fix is a scheduling constraint (node availability, taints, affinity, priority, quota), not a container restart. Check `kubectl describe pod` events and node status before assuming an application-level bug.

## Priority Assignment

Priority should be assigned based on:
- Customer-reported incidents (what has actually broken in production?)
- Production outage patterns (what fault types have the highest blast radius?)
- Compliance and certification requirements (what does the customer SLA cover?)

Faults are canonically defined here. If a fault type appears in a certification experiment, it must have an entry in this taxonomy. If you introduce a new fault type for your deployment, add it here before adding it to the chaos-charts and fault configuration.
